# 第11周学习日志

2026年11月15日—11月21日

这周让我感到变化最大的是，程序开始由几个文件共同组成。以前把类和主函数放在一个文件里，查找起来方便，但内容多了以后，各部分容易挤在一起。课件把声明、实现和主程序分别安排到头文件与源文件中，我逐渐能看出这种组织方式的好处。

头文件可以先交代一个类有哪些数据和操作，源文件再写成员函数的具体实现。主程序包含相应头文件之后，就可以按照声明使用这些功能。我理解，包含头文件主要是让编译器看到需要的声明，真正生成完整程序时，相关源文件中的实现也要参与编译和链接。只把主程序文件交给编译器，有时就会出现找不到函数实现的问题。

这也帮助我区分了编译错误与链接错误。变量名拼错、语句形式不对，通常在编译过程中就会暴露。函数已经声明，但需要的定义没有加入，问题可能到链接时才出现。以后遇到报错，我想先判断它发生在哪个阶段，再检查对应的内容，而不是把所有文件来回改一遍。

预处理的内容里，我比较关注头文件的重复包含。一个头文件可能间接被多次引入，因此需要使用相应的保护写法，避免同一份类定义重复出现。宏的文字替换方式也提醒了我，带参数的宏看起来像函数，处理过程却有区别。对于普通计算，能用清楚的函数表达时，我会先采用函数，减少由括号和替换带来的理解负担。

银行账户实例把这一章的内容串在了一起。账户各自保存自己的余额，多个账户又可以通过静态成员维护共享总额。存款和取款负责改变数据，查询余额这样的操作则适合提供只读接口。日期、利率和累计金额还会参与结息过程，需要按照程序中的计算顺序慢慢看。我觉得这个例子比单独记住 static 或 const 更有帮助，因为可以直接看到这些写法分别解决了什么问题。

回看本周内容，我发现程序文件分开以后，反而更需要把约定保持一致。头文件中的函数声明、源文件中的定义，以及主程序的调用，参数和返回类型都要对应。共享成员也要在合适的位置提供定义。这周我希望自己留下的习惯是，读一个多文件程序时，先找到主函数，再沿着调用关系去看类声明和实现，逐步把整个过程连起来。
